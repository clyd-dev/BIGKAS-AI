Phases 0 and 1 are already done — commit bc85b8c extracted the scoring pipeline into App\Services\AssessmentScorer, with the same signature and the same throw-and-let-the-caller-decide contract this plan specified. 1. What this builds

A teacher sets up one batch covering up to 15 children. Each child's recording is captured either on their own device or by the teacher one at a time. Every recording is queued for analysis, and the teacher tracks the whole group from a single board that reports honest progress and a real time estimate.

Decisions locked

  • Recording modeBatch holds a roster; each child is self (own device) or teacher (teacher-led), set per child.
  • MaterialOne batch default, overridable per child. Grade policy runs per child, unchanged.
  • Assessment typeAll three supported — oral_reading, comprehension, combined — one type per batch.
  • AnalysisEverything queued, on the existing RescoreQueue lane. Live progress board with polling. Teacher may close the laptop and return.
  • GuardrailHard roster cap of 15, plus a wait estimate computed from measured job durations.
  • Single-child flowBehaviour frozen. Batch is a separate route and view; the only change to the existing screen is one added link.
  • VerdictStays per child. No bulk-accept button.

2. Capacity: why the design looks like this

The shape of this feature is dictated by one measurement: local Whisper is CPU-bound and strictly serial. The Random Forest, by contrast, is free.

StageCostRuns in parallel?

ml-service/app.py:87		 ≈1–3 min per 1-minute reading on the VPS CPU; ≈1 GB resident No. Running ten at once thrashes the CPU and slows all ten. This is the bottleneck.
Flask host

RF classify

Alignment & miscue analysis (PHP) fast Fine
Host 4 GB RAM with local Whisper (docs/deployment-vps.md:9) Headroom for one model in memory

Two consequences follow, and they are not negotiable by UI design:

  1. Analysis must leave the HTTP request and run as a queued job on exactly one worker. Ten synchronous analyses would also pin ten PHP‑FPM workers for minutes and gateway-timeout anyway.
  2. "Assess ten at once" is true for recording and false for analysis. Results trickle in over 25–45 minutes. The board must say so rather than spin.
Model quality — why there is no bulk-accept

The shipped RF reports cv_accuracy 0.4993 (±0.105) and test_accuracy 0.625, and class 4 (Reading Comprehension) was trained on 3 samples. Batch assessment multiplies how many of these predictions a teacher sees at once. The board therefore presents RF output as a suggestion awaiting the teacher, keeps the existing per-child verdict step (AssessmentVerdictController) mandatory, and offers no "accept all" control. Ten unreviewed predictions accepted in one click is the single thing this feature must not make easy.

3. The tension, and how it resolved itself

Already done — no work remains in this section

When this plan was drafted, analyze() held ~130 lines of pipeline inside a controller method, and the hard question was how to share it with a background worker without disturbing single-child behaviour. Commit bc85b8c (19 Oct) settled it independently: the pipeline now lives in App\Services\AssessmentScorer and analyze() is 77 lines that delegate to it. The service's own docblock states the contract this plan asked for — "One pipeline for the Analyze button, 'Re-analyze' and the scheduled re-score… It needs no logged-in user, so it can run from the scheduler… It throws when nothing could be measured and the caller decides what to tell whom. It never stands in for a missing engine."

The reasoning below is kept because it still explains why there must be exactly one scoring implementation — the constraint that governs every change in §7.

Single-child behaviour must not change. But analyze() returned HTTP responses from inside the pipeline, and a background worker cannot call a controller action. There were only two routes forward:

ClassificationPagesTest in particular fails if any view or service reads ->primary_weakness directly instead of going through Assessment::weaknessOutcome() — the batch board must obey that too.

4. The new pipeline, in detail

4.1 What already exists

Three callers already share one scoring pipeline, and one of them is already a serial background lane:

  ANALYZE BUTTON            RE-ANALYZE                SCHEDULED RE-SCORE
  POST .../analyze          POST .../reanalyze        assessments:rescore
       │                         │                    (every 5 min, cron)
       │                         │                         │
       │                         │                         ▼
       │                         │                    App\Services\RescoreQueue
       │                         │                     • "the queue is the database"
       │                         │                     • Assessment::awaitingRescore()
       │                         │                     • MAX_ATTEMPTS 3, retry after 10 min
       │                         │                     • engine down ⇒ attempt NOT consumed
       │                         │                         │
       └─────────────────────────┴─────────────────────────┘
                                 ▼
                    App\Services\AssessmentScorer
                      score(Assessment, ?referenceText, ?comprehensionScore): AssessmentResult
                      • knows nothing about HTTP, needs no logged-in user
                      • throws on failure; callers decide what that means
                      • never stands in for a missing engine

4.2 What batch adds — a fourth caller, not a second mechanism

  BATCH (new)
  POST /assessments/batch/{batch}/entry/{assessment}/upload-audio
       │
       │  marks the entry "owed a score" and returns immediately
       ▼
  RescoreQueue  ← extended: batch entries are claimed at once,
       │          not after the 15-minute stale rule
       ▼
  AssessmentScorer   (unchanged)

The scorer is the single source of truth for how a reading is scored; RescoreQueue is the single source of truth for when. Every caller gets identical results because there is only one implementation of each.

Why not Laravel's queue — the bug the draft would have shipped

The draft proposed an AnalyzeAssessmentJob holding each entry in processing while it waited its turn. But Assessment::scopeAwaitingRescore() already claims any recording that is status = 'processing' AND updated_at < now()->subMinutes(15).

A child sitting 14th in a 15-child batch waits roughly 40 minutes in processing. At the 15-minute mark the scheduler would claim that recording and score it concurrently with the worker that already owned it — two Whisper runs, two results racing into createResult(), on a host with headroom for one model. Adding a second background mechanism alongside RescoreQueue is what creates the hazard, so the plan does not add one.

4.3 Inside AssessmentScorer::score()

This is the shipped pipeline as of dbfb7cb. Batch changes none of it. Steps marked NEW are the only additions, and both are additive stamps that leave every existing behaviour alone.

What the caller must do first — the batch caller's obligation

score() takes a comprehension score as a parameter; it does not collect one. Recording the learner's answers via ComprehensionService::record(), and keeping the browser recording via keepRecording(), are the caller's job — today analyze() does both before calling. The ordering is not incidental: answers are stored before any transcription, so a Whisper failure can never cost the learner's answers, and missing answers abort before a minute of CPU is spent. The batch upload endpoint must honour the same order, or a dead engine will throw away a child's comprehension answers.

$assessment->updateStatus(). Note the interaction with awaitingRescore()'s 15-minute stale rule described in §4.2 — this is why batch must not hold entries in processing while they wait.

✕On failure — the pipeline throws; the caller decides
Single-child: unchanged — markFailed(), then 503 with $e->forTeacher() for a dead engine, or 500 with the actionable generic message. Detail goes to the log only.
Batch: nothing new is invented, because RescoreQueue already does exactly what the draft designed from scratch. Its rule: "a failure caused by the engine being unavailable does not use up a recording's attempts — only a recording that fails while the engine is up does." So a dead engine costs the batch nothing and every entry is simply still owed a score; one genuinely bad file is given up on after MAX_ATTEMPTS = 3 rather than retried forever, stays visible to the admin, and the teacher can still press Analyze. A failed child never stops the batch. The recording always survives.

4.4 Batch state machine, per child

The board's chips are a presentation of state the database already holds — derived from status, whether a result exists, its classification_status, whether a verdict exists, and rescore_attempts. No parallel state machine is stored.

waiting ──recording captured──▶ owed a score ──scheduler claims it──▶ scoring
                                (RescoreQueue::due)                      │
                                       ▲                                 │
                                       │ engine was down —               │
                                       │ attempt NOT consumed            │
                                       └─────────────────────────────────┤
                                        ┌────────────────────────────────┘
                                     success                         failure
                                        ▼                               ▼
                                 needs verdict            attempts < 3 ─▶ owed a score
                                        │                 attempts = 3 ─▶ given up
                            teacher decides (per child)                   (Analyze still works)
                                        ▼
                                      done

Batch status: collecting ─▶ analyzing ─▶ completed
                   └──────────────────────▶ cancelled

The batch reaches completed when every entry is terminal (done or given up). A given-up entry does not block completion — it is reported, the teacher can still press Analyze, and the batch moves on.

Note what is no longer needed: the draft's batch-level engine_unavailable status. Because an engine outage does not consume attempts, an outage is not a batch state at all — the entries simply remain owed a score and resume on their own when the engine returns. ServiceHealthMonitor and the health:check schedule already tell the admin the engine is down; the board only needs to surface that, not track it.

4.5 Wait estimate

New App\Services\AnalysisQueueEstimator. Takes the median of the last 20 analysis_duration_ms values (seeded at 150 s until data exists) and multiplies by the depth of RescoreQueue::due() ahead of the given child. Median, not mean, so one 5-minute outlier does not distort every estimate on screen.

Two honesty terms the draft did not have to account for, both consequences of a scheduler-driven lane rather than a resident worker:

  • Tick latency. Work starts on the next assessments:rescore run, so the estimate must add up to one tick interval. This is the real cost of reusing RescoreQueue, and §8 covers how the tick and --limit get tuned for a 15-child batch.
  • Other teachers' recordings. due() is global, so a batch genuinely queues behind other classes' work — which the board already intended to say.

The board shows this as "about 18 min remaining · 4 ahead of you from other classes". Teachers self-regulate when they can see the truth, and a slow lane becomes distinguishable from a broken one.

Already present — reused, not re-added

rescore_attempts and last_rescore_at already exist on assessments (shipped with RescoreQueue), and classification_status already exists on assessment_results. Batch reads all three and adds none of them. The draft's queued_at is dropped — last_rescore_at plus the awaitingRescore scope already express everything the board needs.

Deliberately not added

  • No roster-entry table. A roster entry is an Assessment. Per-child material override is simply that child's existing material_id.
  • No join-code table. Self-record reuses one AssessmentSession per entry, with the existing generateCode() and student join flow.
  • No STATUS_QUEUED constant. The draft added one. It is now unnecessary and actively harmful: "owed a score" is already expressed by Assessment::scopeAwaitingRescore(), and a sixth status would need auditing against every existing status check for no gain. Dropped.
  • No jobs / failed_jobs usage. app/Jobs/ stays empty. The lane is the scheduler plus the database, as it already is.
The one place to be careful — the awaitingRescore scope

Batch needs its entries claimed promptly, whereas the scope today claims an unscored recording only once it is failed, or processing and stale by 15 minutes. Widening that scope is the single riskiest edit in this plan, because RescoreQueue is shared with the outage-recovery path that already works in production.

It will be widened additively — a batch entry is owed a score the moment its audio is saved — and RescoreQueueTest must stay green with no edits, proving the outage-recovery behaviour is unchanged for non-batch recordings.

6. Teacher-facing UI

Built on the existing staff shell and <x-page-header>. The board is a nav page, so no back link; each child drills down to the existing results screen with a back link labelled "Batch", per the house rule that PageHeaderTest enforces.

Entry point

/assessments/new gains one added link — "Assess a group" — pointing at the new assessments/batch/create. The existing single-learner screen is otherwise not modified.

Batch setup — /assessments/batch/create

Pick a class or hand-pick learners → language → type → default material → a roster table where each row can override the material and choose self or teacher. The cap comes from config('assessment.batch_max_learners'), default 15, enforced in validation with a clear message. Grade policy runs per child under today's rules: a cross-grade child must be ticked individually, never silently.

Batch board — /assessments/batch/{batch}

The roster, polling /batch/{batch}/poll — the same polling pattern as the existing pollSession, so no new transport. Each row shows a state chip (waiting / recorded / queued / transcribing / needs verdict / done / failed), the ETA, and one action.

  • Teacher-led rows record inline, reusing _audio_capture.blade.php.
  • Self-record rows display the child's join code.
  • Comprehension answers come from the child's own device in self mode, or from an inline per-child panel in teacher-led mode — posted through the existing ComprehensionService path before the job is queued.
  • Failed rows offer per-child Retry, with today's retry semantics.

8. Throughput tuning — and the lock that must not be ignored

Reusing RescoreQueue removes a deploy change but introduces a tuning problem. Today's schedule is built for trickle recovery after an outage, not for 15 recordings arriving at once:

Schedule::command('assessments:rescore')->everyFiveMinutes()->withoutOverlapping(30);
// signature: assessments:rescore {--limit=5}
SettingTodayEffect on a 15-child batch
Tick interval5 minUp to 5 minutes of dead air before the first child is even picked up, and a gap after every run.
--limit5One run scores at most 5, taking 5–15 min. Fifteen children need three runs.
withoutOverlapping30 minThe hazard. This is a lock expiry, not a guarantee.
Raising --limit without raising the lock re-creates the double-scoring bug

withoutOverlapping(30) means the lock is released after 30 minutes whether the run finished or not. At --limit=5 a run takes at most ~15 minutes and this never matters. But a naive "just raise the limit to 15" gives a run of up to 45 minutes — the lock expires at 30, the next tick starts a second concurrent run, and two Whisper processes fight over one model's worth of RAM, scoring the same recordings twice.

The rule: --limit × worst-case per-recording time must stay comfortably below the withoutOverlapping window. Any change to one requires changing the other, and the plan treats them as a single setting.

Proposed settings

Schedule::command('assessments:rescore --limit=8')
    ->everyMinute()
    ->withoutOverlapping(45);

Three deliberate choices:

  • everyMinute, not everyFiveMinutes. Counter-intuitive but correct: withoutOverlapping already prevents pile-up, so a one-minute tick means "start again as soon as the lane is free" rather than "idle until the next multiple of five". This removes nearly all tick latency and the between-run gaps, and costs nothing when there is no work — the command exits immediately.
  • --limit=8. Worst case 8 × 3 min = 24 min, safely inside a 45-minute lock. Two runs clear a full 15-child batch.
  • withoutOverlapping(45). Nearly double the worst-case run, so the lock protects rather than merely delays.

These numbers are a starting point to be confirmed against the Phase 3 measurement, not an assumption. Once analysis_duration_ms has real data, the estimator's own median is the right basis for a final value — and the cron prerequisite (schedule:run every minute) is already documented in routes/console.php.

Retired from the draft — and still worth knowing

The draft's §8 flagged that bigkas_first_day_setup.sh:285 installs queue:work with Laravel's default 60-second job timeout, which would kill any 300-second Whisper job. That fix is no longer part of this work, because nothing here puts anything on Laravel's queue and app/Jobs/ stays empty.

The misconfiguration is still there, still harmless, and still a trap for whoever first adds a real job to this project. Worth fixing on its own someday; not in this plan's scope.

9. Backup & rollback

Six independent ways back, strongest first. The first two mean that in the common case nothing has to be rolled back at all.

9.1 Feature flag — the instant off switch

BATCH_ASSESSMENT_ENABLED=false behind config('assessment.batch_enabled') hides the "Assess a group" link and makes every batch route 404. The single-child flow is untouched code either way, so it keeps working.

This ships off. It is turned on deliberately, and turning it back off takes one .env edit — no code rollback, no migration rollback, no downtime. Remember that an .env edit does nothing until config:cache runs again.

9.2 Branch + tag

Before any work starts:

# on the dev machine, from clean master
git tag -a pre-batch-assessment -m "Last state before batch assessment work"
git push origin pre-batch-assessment
git switch -c feat/batch-assessment

master is never committed to during the build. The tag is a permanent, named return point — the repo has no tags today, so this is also the project's first.

9.3 One commit per phase

Each phase lands as its own commit, each independently green. Rollback granularity is therefore a phase, not the whole feature. Phase 1 in particular — the pipeline extraction — is behaviour-neutral and committed alone, so if anything about it smells, that single commit reverts without touching the schema or the queue.

9.4 Database

Every schema change is additive: one new table, and nullable columns on assessments. Nothing is renamed, retyped or dropped, so no existing data can be lost and down() is genuinely safe. Each migration's down() is written and exercised (migrate:rollback) before the phase is called done.

On the VPS, before migrating:

# dump first — takes seconds, and is the thing you will wish you had
mysqldump -u <user> -p <database> > ~/backups/bigkas-$(date +%F-%H%M).sql

php artisan migrate
# if it goes wrong:
php artisan migrate:rollback --step=1

Recorded audio under storage/app/public/assessments/audio is only ever added to by this work, never deleted or rewritten, so it needs no special handling. A routine copy alongside the dump costs nothing if you want belt and braces.

9.5 Full VPS rollback procedure

If the feature flag is not enough and the deployment itself has to go back:

cd /var/www/bigkas-ai

php artisan down                      # maintenance mode

git checkout pre-batch-assessment     # or: git checkout master
php artisan migrate:rollback --step=<n>   # only if migrations had run

# all THREE caches, always — not the subset the change looks like it needs
php artisan config:clear && php artisan config:cache
php artisan route:clear  && php artisan route:cache
php artisan view:clear   && php artisan view:cache

sudo systemctl restart bigkas-queue   # drop any job referencing removed code
sudo systemctl restart php8.3-fpm

php artisan up
Do not skip a cache rebuild

On 8 October 2026 a pull was deployed with only config:cache and view:clear. A new route was missing from the stale bootstrap/cache/routes-v7.php, so route() threw inside a Blade view and the admin dashboard 500'd — with a stack trace pointing at View->renderContents(), which reads like a view bug and sends you hunting in the wrong file. A rollback removes routes, which is exactly the same trap in reverse. php artisan optimize does all three; optimize:clear is the inverse.

To read a 500 there, tail is useless (Laravel writes one long line):
grep -oE '(local|production)\.(ERROR|CRITICAL):.{0,500}' storage/logs/laravel.log | tail -2

9.6 Stopping the lane before a rollback

Reusing RescoreQueue makes this markedly simpler than the draft's version, because there is no serialized job payload to go stale. As its docblock puts it: "Nothing is held anywhere else, so nothing can be lost from a queue that was never written." Pending work is just rows that match a scope — roll the code back and the scope reverts with it.

So there is nothing to drain and nothing to clear. The only requirement is that a scoring run is not mid-flight while the code changes underneath it:

# 1. stop the scheduler from starting another run
sudo crontab -e        # comment out the `schedule:run` line
#    (or, if the cron entry is in /etc/cron.d/, move the file aside)

# 2. let any in-flight run finish — it is at most one recording away from done
ps aux | grep '[a]ssessments:rescore'

# 3. roll back (§9.5), then restore the cron line

No learner data is at risk at any point. Audio and comprehension answers are persisted the moment they arrive; a rollback mid-batch leaves every recording on disk, still owed a score, and the single-child Analyze button can score any of them by hand. A batch interrupted by a rollback resumes by itself once the cron line is restored.

If the rollback crosses the Phase 2 migration

migrate:rollback drops batch_id. Entries that were owed a score because they were batch entries become ordinary unscored recordings, which the original awaitingRescore rules will claim only once they are failed or 15-minutes stale in processing. They are not lost — they are merely slower to be picked up, and Analyze still works on each. Worth telling the teacher rather than letting them think the batch vanished.

10. Out of scope

Each of these is a clean follow-up once the queue is proven in a real classroom — none is blocked by this design.

  • Parallel Whisper. CPU-bound, ≈1 GB resident per model, 4 GB host. Concurrency 1 is the correct setting, not a limitation to work around.
  • Fixing the queue:work timeout in the systemd unit (§8) — latent, harmless, and no longer touched by this work.
  • GPU inference. Different hosting conversation entirely.
  • Websockets / live push. Polling matches the existing pollSession and needs no new infrastructure.
  • Batch-level PDF or Form 3 export. Per-child export already works.
  • Cross-batch analytics and trend comparison.
  • Bulk verdict acceptance. Excluded on purpose — see §2.
The expectation to set with teachers

A 15-child batch is roughly 25–45 minutes of transcription after the last child stops reading. This design makes that wait visible, interruptible and safe to walk away from. It does not make it shorter — on this hardware, nothing in software can.
