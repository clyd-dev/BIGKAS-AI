Revision note — 22 October 2026 (rev. 5): the join code is a reference, not a way in

What this document promised. Seven places in this plan — the Recording mode decision in §1, the dropped recording_mode note in §6, the card-panel figure and its caption, the waiting row of the seven-states table, the waiting row of the cancel-and-remove table, and the batch-cancel list — describe a join code as one of the two routes a recording can be captured by: “a join code for a child with a device”, “its join code stops working”. Read plainly, that promises a screen where a child types a code and starts reading.

What was built. There is no code-entry screen, and no screen anywhere in this application accepts a code. A child reaches their reading the one way they reach everything else: they sign in with their own PIN, and the reading the teacher set up is waiting on their dashboard (StudentAssessmentController::pendingFor()). The code is still issued — one AssessmentSession per entry, created with the batch — and the board and the card panel still show it, but only as a reference for the teacher’s own records, which is how both screens now label it. Nothing in the system reads it back.

Why a code-entry screen was declined. It was considered. A code box that starts a reading is an unauthenticated door onto a named child’s assessment: anyone holding six characters — a classmate, a sibling, anyone who saw the board over a shoulder — could open that child’s reading and record audio against their record, with no sign-in and nothing tying the recording to the child it is filed under. The child is already authenticated by their PIN, and their dashboard already knows what they owe, so the door would add a weaker way in to reach something the stronger way already reaches. The measurement is about a child; its provenance has to be at least as strong as the rest of their record.

So, for the next reader: wherever this plan says join code, read session code, shown to the teacher for her records. “Its join code stops working” means only that the session row is deleted with the entry — nothing stopped working for the child, because nothing was ever typed in. Do not build the code-entry screen on the strength of the sentences below; they are the draft’s language, kept so the history reads honestly, each marked rev 5. The rest of this plan stands as written.

1. What this builds

A teacher sets up one batch covering up to 15 children. Each child's recording is captured either on their own device or by the teacher one at a time. Every recording is queued for analysis, and the teacher tracks the whole group from a single board that reports honest progress and a real time estimate.

Decisions locked

  • Recording modeNot chosen in advance. Every child's card offers both — a join code for a child with a device, and Conduct here for a child without one. The teacher decides in the moment. rev 5
  • Before analysisA recording rests at recorded with its audio playable. The teacher listens, then Send for analysis — or re-records. Nothing reaches the lane unsent.
  • Leaving the pageChanges nothing. Scoring runs server-side under cron, and the batch completes itself with nobody watching.
  • Cancel & removeEvery card can be cancelled or removed, and the batch cancelled behind a confirmation. Nothing on this board can destroy a measured reading — real deletion lives on the child's learner-history screen.
  • MaterialOne batch default, overridable per child. Grade policy runs per child, unchanged.
  • Assessment typeAll three supported — oral_reading, comprehension, combined — one type per batch.
  • AnalysisEverything queued, on the existing RescoreQueue lane. Live progress board with polling. Teacher may close the laptop and return.
  • GuardrailHard roster cap of 15, plus a wait estimate computed from measured job durations.
  • Single-child flowBehaviour frozen. Batch is a separate route and view; the only change to the existing screen is one added link.
  • VerdictStays per child. No bulk-accept button.

2. Capacity: why the design looks like this

The shape of this feature is dictated by one measurement: local Whisper is CPU-bound and strictly serial. The Random Forest, by contrast, is free.

Two consequences follow, and they are not negotiable by UI design:

  1. Analysis must leave the HTTP request and run as a queued job on exactly one worker. Ten synchronous analyses would also pin ten PHP‑FPM workers for minutes and gateway-timeout anyway.
  2. "Assess ten at once" is true for recording and false for analysis. Results trickle in over 25–45 minutes. The board must say so rather than spin.
Model quality — why there is no bulk-accept

The shipped RF reports cv_accuracy 0.4993 (±0.105) and test_accuracy 0.625, and class 4 (Reading Comprehension) was trained on 3 samples. Batch assessment multiplies how many of these predictions a teacher sees at once. The board therefore presents RF output as a suggestion awaiting the teacher, keeps the existing per-child verdict step (AssessmentVerdictController) mandatory, and offers no "accept all" control. Ten unreviewed predictions accepted in one click is the single thing this feature must not make easy.

3. The tension, and how it resolved itself

Already done — no work remains in this section

When this plan was drafted, analyze() held ~130 lines of pipeline inside a controller method, and the hard question was how to share it with a background worker without disturbing single-child behaviour. Commit bc85b8c (19 Oct) settled it independently: the pipeline now lives in App\Services\AssessmentScorer and analyze() is 77 lines that delegate to it. The service's own docblock states the contract this plan asked for — "One pipeline for the Analyze button, 'Re-analyze' and the scheduled re-score… It needs no logged-in user, so it can run from the scheduler… It throws when nothing could be measured and the caller decides what to tell whom. It never stands in for a missing engine."

The reasoning below is kept because it still explains why there must be exactly one scoring implementation — the constraint that governs every change in §7.

Single-child behaviour must not change. But analyze() returned HTTP responses from inside the pipeline, and a background worker cannot call a controller action. There were only two routes forward:

The refactor arrived with its own net, and the suite has grown since the draft: ClassificationOutcomeTest, ClassificationPagesTest, ClassifierProvenanceTest, NotMeasuredTest, RescoreQueueTest and SpeechEngineRequiredTest now sit alongside ReanalyzeAssessmentTest, RecordingKeptTest, WeaknessMatchesEvidenceTest, MiscueDetectionTest, ComprehensionTestTest and DecisionSupportTest.

If a test has to change to go green, single-child behaviour changed, and the batch change is wrong. ClassificationPagesTest in particular fails if any view or service reads ->primary_weakness directly instead of going through Assessment::weaknessOutcome() — the batch board must obey that too.

4. The new pipeline, in detail

4.1 What already exists

Three callers already share one scoring pipeline, and one of them is already a serial background lane:

  ANALYZE BUTTON            RE-ANALYZE                SCHEDULED RE-SCORE
  POST .../analyze          POST .../reanalyze        assessments:rescore
       │                         │                    (every 5 min, cron)
       │                         │                         │
       │                         │                         ▼
       │                         │                    App\Services\RescoreQueue
       │                         │                     • "the queue is the database"
       │                         │                     • Assessment::awaitingRescore()
       │                         │                     • MAX_ATTEMPTS 3, retry after 10 min
       │                         │                     • engine down ⇒ attempt NOT consumed
       │                         │                         │
       └─────────────────────────┴─────────────────────────┘
                                 ▼
                    App\Services\AssessmentScorer
                      score(Assessment, ?referenceText, ?comprehensionScore): AssessmentResult
                      • knows nothing about HTTP, needs no logged-in user
                      • throws on failure; callers decide what that means
                      • never stands in for a missing engine

4.2 What batch adds — a fourth caller, not a second mechanism

  BATCH (new)
  POST .../entry/{assessment}/upload-audio      teacher records, or child self-records
       │
       │  audio saved — card shows "recorded", audio playable
       ▼
  POST .../entry/{assessment}/send              teacher listens, then releases it
       │
       │  stamps submitted_for_analysis_at, returns immediately
       ▼
  RescoreQueue  ← extended: a SENT batch entry is claimed at once,
       │          not after the 15-minute stale rule
       ▼
  AssessmentScorer   (unchanged)

The scorer is the single source of truth for how a reading is scored; RescoreQueue is the single source of truth for when. Every caller gets identical results because there is only one implementation of each.

Why not Laravel's queue — the bug the draft would have shipped

The draft proposed an AnalyzeAssessmentJob holding each entry in processing while it waited its turn. But Assessment::scopeAwaitingRescore() already claims any recording that is status = 'processing' AND updated_at < now()->subMinutes(15).

A child sitting 14th in a 15-child batch waits roughly 40 minutes in processing. At the 15-minute mark the scheduler would claim that recording and score it concurrently with the worker that already owned it — two Whisper runs, two results racing into createResult(), on a host with headroom for one model. Adding a second background mechanism alongside RescoreQueue is what creates the hazard, so the plan does not add one.

4.3 Inside AssessmentScorer::score()

This is the shipped pipeline as of dbfb7cb. Batch changes none of it. Steps marked NEW are the only additions, and both are additive stamps that leave every existing behaviour alone.

What the caller must do first — the batch caller's obligation

score() takes a comprehension score as a parameter; it does not collect one. Recording the learner's answers via ComprehensionService::record(), and keeping the browser recording via keepRecording(), are the caller's job — today analyze() does both before calling. The ordering is not incidental: answers are stored before any transcription, so a Whisper failure can never cost the learner's answers, and missing answers abort before a minute of CPU is spent. The batch upload endpoint must honour the same order, or a dead engine will throw away a child's comprehension answers.

✕On failure — the pipeline throws; the caller decides
Single-child: unchanged — markFailed(), then 503 with $e->forTeacher() for a dead engine, or 500 with the actionable generic message. Detail goes to the log only.
Batch: nothing new is invented, because RescoreQueue already does exactly what the draft designed from scratch. Its rule: "a failure caused by the engine being unavailable does not use up a recording's attempts — only a recording that fails while the engine is up does." So a dead engine costs the batch nothing and every entry is simply still owed a score; one genuinely bad file is given up on after MAX_ATTEMPTS = 3 rather than retried forever, stays visible to the admin, and the teacher can still press Analyze. A failed child never stops the batch. The recording always survives.

4.4 Batch state machine, per child

The board's chips are a presentation of state the database already holds — derived from status, whether a result exists, its classification_status, whether a verdict exists, and rescore_attempts. No parallel state machine is stored.

                                            ▼                                    ▼

                                            ▼
                                          done

Batch status: collecting ─▶ analyzing ─▶ completed
                   └──────────────────────▶ cancelled

The batch reaches completed when every entry is terminal (done or given up). A given-up entry does not block completion — it is reported, the teacher can still press Analyze, and the batch moves on.

Note what is no longer needed: the draft's batch-level engine_unavailable status. Because an engine outage does not consume attempts, an outage is not a batch state at all — the entries simply remain owed a score and resume on their own when the engine returns. ServiceHealthMonitor and the health:check schedule already tell the admin the engine is down; the board only needs to surface that, not track it.

4.5 Wait estimate

New App\Services\AnalysisQueueEstimator. Takes the median of the last 20 analysis_duration_ms values (seeded at 150 s until data exists) and multiplies by the depth of RescoreQueue::due() ahead of the given child. Median, not mean, so one 5-minute outlier does not distort every estimate on screen.

Two honesty terms the draft did not have to account for, both consequences of a scheduler-driven lane rather than a resident worker:

  • Tick latency. Work starts on the next assessments:rescore run, so the estimate must add up to one tick interval. This is the real cost of reusing RescoreQueue, and §8 covers how the tick and --limit get tuned for a 15-child batch.
  • Other teachers' recordings. due() is global, so a batch genuinely queues behind other classes' work — which the board already intended to say.

The board shows this as "about 18 min remaining · 4 ahead of you from other classes". Teachers self-regulate when they can see the truth, and a slow lane becomes distinguishable from a broken one.

The original assessments table uses enum() for language, status and assessment_type. Indexes added to assessments:

  • batch_id — the board loads one batch's entries on every poll; this is the hottest new query in the feature.
  • Composite (batch_id, submitted_for_analysis_at) — serves queries that filter a batch's entries by whether they have been sent: the board, the estimator, and the widened awaitingRescore branch read in isolation.
Correction — what the composite index does not buy

An earlier revision claimed this index stops awaitingRescore scanning assessments every scheduler tick. It does not. That scope is a disjunction — the batch branch is OR‑ed with unindexed status and updated_at conditions and with doesntHave(), which compiles to NOT EXISTS — and a planner generally cannot drive an index through an OR of that shape. EXPLAIN QUERY PLAN on SQLite reports SCAN assessments with the index in place.

The scan was already happening before batch assessment existed, so nothing regressed, and audio_file IS NOT NULL already limits the rows examined. At one school’s volume — hundreds to low thousands of assessments — a scan once a minute is not a cost worth restructuring the scope for. The indexes still earn their place on the board’s own where batch_id = ? query, which is the genuinely hot one. Verify with a MySQL EXPLAIN on realistic data before relying on either claim; rewriting the batch branch as a UNION would be a bigger change and is not warranted now.

Not indexed, on purpose: analysis_started_at and analysis_duration_ms. The estimator reads at most the last 20 rows ordered by id, and the transcribing check is always already narrowed by batch_id.

Dropped from the draft: recording_mode

rev 5 The draft stored self / teacher per child, chosen at setup. The column is gone. Every card now offers both a join code and Conduct here, so there is nothing to record in advance — the teacher decides per child in the moment, which is how a classroom actually behaves. This removes a column, a setup decision, a validation path and a whole class of "the teacher guessed wrong at setup" problem.

Already present — reused, not re-added

rescore_attempts and last_rescore_at already exist on assessments (shipped with RescoreQueue), and classification_status already exists on assessment_results. Batch reads all three and adds none of them. The draft's queued_at is dropped — last_rescore_at plus the awaitingRescore scope already express everything the board needs.

Deliberately not added

  • No roster-entry table. A roster entry is an Assessment. Per-child material override is simply that child's existing material_id.
  • No join-code table. Self-record reuses one AssessmentSession per entry, with the existing generateCode() and student join flow.
  • No STATUS_QUEUED constant. The draft added one. It is now unnecessary and actively harmful: "owed a score" is already expressed by Assessment::scopeAwaitingRescore(), and a sixth status would need auditing against every existing status check for no gain. Dropped.
  • No jobs / failed_jobs usage. app/Jobs/ stays empty. The lane is the scheduler plus the database, as it already is.
  • No recording_mode. See above.
  • No per-entry state column. All seven card states are derived (§6). Storing them would create a second truth that can disagree with the data.
The one place to be careful — the awaitingRescore scope

Batch needs its entries claimed promptly once sent, whereas the scope today claims an unscored recording only once it is failed, or processing and stale by 15 minutes. Widening that scope is the single riskiest edit in this plan, because RescoreQueue is shared with the outage-recovery path that already works in production.

The new branch is narrow and additive: batch_id IS NOT NULL AND submitted_for_analysis_at IS NOT NULL and no result. The failed and stale-processing conditions are left exactly as they are, so a non-batch recording behaves identically. RescoreQueueTest must stay green with no edits, proving it.

The submitted_for_analysis_at gate does more than serve the UI: it means a half-finished batch cannot leak into the lane. A teacher who sets up fifteen children and records three has three recordings in the system and nothing queued until they say so.

6. Teacher-facing UI

Built on the existing staff shell and <x-page-header>. The board is a nav page, so no back link; each child drills down to the existing results screen with a back link labelled "Batch", per the house rule that PageHeaderTest enforces.

Entry point

/assessments/new gains one added link — "Assess a group" — pointing at the new assessments/batch/create. The existing single-learner screen is otherwise not modified.

Batch setup — /assessments/batch/create

Pick a class or hand-pick learners → language → type → default material → a roster list where each child's material can be overridden. No recording-mode choice — that is decided per card, in the moment. The cap comes from config('assessment.batch_max_learners'), default 15, enforced in validation with a clear message. Grade policy runs per child under today's rules: a cross-grade child must be ticked individually, never silently.

Batch board — /assessments/batch/{batch}

A card per child, in a responsive grid, polling /batch/{batch}/poll — the same polling pattern as the existing pollSession, so no new transport. Each card carries the child's name, a state chip, and the one action that state calls for. The whole card is clickable and opens that child's panel.

Audio is playable in the card from recorded onward — not only at recorded. Once a recording exists the teacher can always hear what was captured, including after it is scored, which is what makes a surprising result checkable.

Two honesty rules this board must not break

An outage is not a failure. RescoreQueue::rescore() calls markFailed() when the engine is down, deliberately leaving the attempt uncounted. An entry whose status is failed but which awaitingRescore() still claims reads as queued, waiting for the speech engine — never failed. Rendering raw status would tell a teacher that ten children failed when nothing did.

An unclassified result is not done. A result with classification_status = 'unavailable' has measurements but no weakness label, so it stays queued — waiting for the model — and the card says so. It must never present as finished.

Comprehension, and the Send gate

For a comprehension or combined batch, the card panel carries the question set. Answers are recorded through the existing ComprehensionService before Send for analysis becomes available — which means the spec's ordering obligation (§4.3) is enforced by the UI rather than merely hoped for: a dead engine can never discard a child's answers, because the answers were stored before anything was sent.

Leaving the page must not stop the work

Nothing about analysis lives in the browser. A recording is scored by assessments:rescore under cron, on the server, so closing the laptop, pressing Back, losing Wi-Fi or shutting the lid changes nothing — the lane keeps working and the results are waiting when the teacher returns. The board is a window onto server state, never the engine driving it.

A flaw in the draft that this requirement exposed

The draft had AssessmentBatch::refreshStatus() called from poll(). Scoring would have continued correctly with the page closed — but the batch's own status would have frozen at analyzing until somebody reopened the board, so a batch that finished overnight would still claim to be running.

Fixed by moving it to an observer on Assessment: when an entry gains a result or exhausts its attempts, its batch refreshes itself. The batch now completes with nobody watching, and poll() only reads. A stored status that only updates while someone is looking at it is not a stored status, it is a rendering artefact.

The board says so plainly, so the teacher does not sit and wait out of doubt: "Analysis continues even if you close this page — you can come back any time."

The one thing that is not safe, stated rather than glossed: a recording still being captured in the card panel exists only in the browser until it is uploaded. If the laptop closes mid-reading, that recording is lost and the child reads again. Everything that reached the server is safe, including recordings that are recorded but not yet sent.

queuedCancel analysisClears submitted_for_analysis_at, so the lane stops taking it, and the card returns to recorded with its audio intact. The true "I sent that by mistake".
transcribingnoneA running Whisper process cannot be aborted honestly. The card says "being analysed now — about N min left" and offers nothing, rather than a button that would not do what it says.
needs verdict · doneRemove from batchSets batch_id to null and nothing more. The card leaves the board; the assessment, result, verdict and comprehension answers all survive and stay reachable from the child's learner history. Their reading level is unaffected.
failedRemove from batchAlso batch_id to null, keeping the recording so the teacher can still press Analyze from the child's history.
Why "remove from batch" and not "delete"

Deleting an Assessment cascade-deletes its assessment_results, assessment_verdicts, comprehension_answers and assessment_sessions rows. Worse, Learner::readingLevelFromAssessments() derives the child's reading level from their assessments, so a delete silently changes that child's level — which is what parents see, what Practice Center recommends from, what interventions are chosen on, and what the admin chart counts.

That is far too much consequence for a button on a card. Destroying a reading lives on the child's own learner-history screen instead, where the teacher sees the whole record they are about to remove rather than one card among fifteen, and confirms it there.

Cancelling the whole batch

Behind a confirmation dialog naming what will and will not be affected — "Cancel this batch? 4 children already assessed keep their results. 6 waiting and 5 queued will be stopped." On confirm:

  • Batch status becomes cancelled, stamped with cancelled_at
  • Every queued entry is un-sent, so the lane stops taking them
  • Entries with no recording are removed, and their join codes stop working rev 5
  • Every child already scored keeps their reading, in their own history
  • An entry mid-transcribing is left to finish; its result is kept, because it cost the time either way and the measurement is valid

Cancelling abandons the session, not the measurements. A teacher who cancels because the bell rang has not thrown away the nine children who did read.

One bulk action, and only one

The board offers Send all ready — releasing every recorded card at once, for the common case where fifteen children read simultaneously on their own devices and the teacher reviews them in a batch.

This is deliberately not a contradiction of §2's no-bulk-accept rule, and the distinction matters: sending a recording for analysis asks the machine to measure something, and a bad send costs lane time. Accepting a verdict records a judgement about a child in their permanent record. The first is safe to do fifteen at a time; the second never is.

8. Throughput tuning — and the lock that must not be ignored

Reusing RescoreQueue removes a deploy change but introduces a tuning problem. Today's schedule is built for trickle recovery after an outage, not for 15 recordings arriving at once:

Schedule::command('assessments:rescore')->everyFiveMinutes()->withoutOverlapping(30);
// signature: assessments:rescore {--limit=5}
SettingTodayEffect on a 15-child batch
Tick interval5 minUp to 5 minutes of dead air before the first child is even picked up, and a gap after every run.
--limit5One run scores at most 5, taking 5–15 min. Fifteen children need three runs.
withoutOverlapping30 minThe hazard. This is a lock expiry, not a guarantee.
Raising --limit without raising the lock re-creates the double-scoring bug

withoutOverlapping(30) means the lock is released after 30 minutes whether the run finished or not. At --limit=5 a run takes at most ~15 minutes and this never matters. But a naive "just raise the limit to 15" gives a run of up to 45 minutes — the lock expires at 30, the next tick starts a second concurrent run, and two Whisper processes fight over one model's worth of RAM, scoring the same recordings twice.

The rule: --limit × worst-case per-recording time must stay comfortably below the withoutOverlapping window. Any change to one requires changing the other, and the plan treats them as a single setting.

Settings

Schedule::command('assessments:rescore --limit=20')
    ->everyMinute()
    ->withoutOverlapping(120);
SettingWasNowWhy
--limit520A full 15-child batch clears in one run, with room for a few single assessments alongside it. At 5 it took three runs.
worst-case run15 min60 min20 × 3 min.
× 1.5 margin22.5 min90 minThe figure the lock must clear.
withoutOverlapping30 min120 minComfortably above 90, so the lock protects rather than merely delays.
tick5 min1 minSee below.

everyMinute, not everyFiveMinutes — counter-intuitive but correct. withoutOverlapping already prevents pile-up, so a one-minute tick means "start again as soon as the lane is free" rather than "idle until the next multiple of five". It removes nearly all tick latency and every between-run gap, and costs nothing when there is no work: the command exits immediately.

What a 60-minute run costs, stated plainly

A 15-child batch holds the single lane for up to an hour. Another teacher's one-off assessment, created mid-batch, waits behind it. RescoreQueue already orders oldest('id') first, so this is fair FIFO rather than starvation — but with one serial lane, fair still means slow. This is inherent to the hardware (§2), not a defect, and it is the price of clearing a batch in one run instead of three.

A 120-minute lock is a 120-minute liability if the process dies

withoutOverlapping releases its cache lock on normal exit, but a SIGKILL — an OOM kill, a systemctl stop mid-run, a reboot — leaves the lock sitting there. Until it expires, nothing is rescored at all, including outage recovery for ordinary single-child assessments. At the old 30 minutes that was an annoyance; at 120 it is half a school day.

The unstick command must be in the runbook and in docs/deployment-vps.md:

php artisan schedule:clear-cache

The symptom to document alongside it: recordings sitting at queued with the engine demonstrably healthy, and no Rescored assessment lines appearing in the log.

These numbers are a starting point to be confirmed against the Phase 3 measurement, not an assumption. Once analysis_duration_ms holds real data the estimator's own median is the right basis for a final value — and if the measured worst case per recording exceeds 3 minutes, --limit=20 breaches the invariant and both numbers must move together. The cron prerequisite (schedule:run every minute) is already documented in routes/console.php.

Retired from the draft — and still worth knowing

The draft's §8 flagged that bigkas_first_day_setup.sh:285 installs queue:work with Laravel's default 60-second job timeout, which would kill any 300-second Whisper job. That fix is no longer part of this work, because nothing here puts anything on Laravel's queue and app/Jobs/ stays empty.

The misconfiguration is still there, still harmless, and still a trap for whoever first adds a real job to this project. Worth fixing on its own someday; not in this plan's scope.

9. Backup & rollback

Six independent ways back, strongest first. The first two mean that in the common case nothing has to be rolled back at all.

9.1 Feature flag — the instant off switch — REQUIRED, LANDS BEFORE ANY UI

BATCH_ASSESSMENT_ENABLED=false behind config('assessment.batch_enabled') hides the "Assess a group" link and makes every batch route 404 via a batch.enabled middleware. The single-child flow is untouched code either way, so it keeps working.

This is not an optional nicety and not a late addition: the flag and its middleware land in Task 5, before any batch screen exists, and the task's own tests assert that the default is false and that every batch route 404s when it is off. No batch UI is written until that is proven.

This ships off. It is turned on deliberately, and turning it back off takes one .env edit — no code rollback, no migration rollback, no downtime. Remember that an .env edit does nothing until config:cache runs again.

9.2 Branch + tag — DONE

git tag -a pre-batch-assessment -m "Last state before batch assessment work"   # done
git push origin pre-batch-assessment                                           # done
git switch -c feat/batch-assessment                                            # done

master is never committed to during the build. The tag is a permanent, named return point, pushed to origin — the repo had no tags before, so this is also the project's first.

9.3 A branch per phase, merged into an integration branch

Every phase gets its own branch. Nothing is committed to master at any point.

master                                      ← untouched throughout
  │
  └── feat/batch-assessment                 ← integration branch (already cut)
        │
        ├── feat/batch-t01-schema      ──merge --no-ff──▶
        ├── feat/batch-t02-claim       ──merge --no-ff──▶
        ├── feat/batch-t03-estimator   ──merge --no-ff──▶
        └── …                               one branch per task

Each task branches off the current integration branch, is proven green on its own, and merges back with --no-ff. The tasks are sequentially dependent — Task 8 consumes Task 3's estimator, Task 9 consumes Task 8's card states — so they cannot be developed in parallel isolation; branching off the integration branch each time is what keeps each one reviewable without pretending they are independent.

--no-ff matters: it means every phase stays a single, named, revertible merge commit. Rollback granularity is a phase, not the whole feature:

git revert -m 1 <merge-commit>     # undo exactly one phase, keep the rest
git switch feat/batch-assessment && git reset --hard <earlier-merge>   # or rewind to a phase boundary

Merging the finished feature into master is a separate, explicit decision taken after §9.5's measured run — never a side effect of finishing a task.

9.4 Database

Every schema change is additive: one new table, and nullable columns on assessments. Nothing is renamed, retyped or dropped, so no existing data can be lost and down() is genuinely safe. Each migration's down() is written and exercised (migrate:rollback) before the phase is called done.

On the VPS, before migrating:

# dump first — takes seconds, and is the thing you will wish you had
mysqldump -u <user> -p <database> > ~/backups/bigkas-$(date +%F-%H%M).sql

php artisan migrate
# if it goes wrong:
php artisan migrate:rollback --step=1

Recorded audio under storage/app/public/assessments/audio is only ever added to by this work, never deleted or rewritten, so it needs no special handling. A routine copy alongside the dump costs nothing if you want belt and braces.

9.5 Full VPS rollback procedure

If the feature flag is not enough and the deployment itself has to go back:

cd /var/www/bigkas-ai

php artisan down                      # maintenance mode

git checkout pre-batch-assessment     # or: git checkout master
php artisan migrate:rollback --step=<n>   # only if migrations had run

# all THREE caches, always — not the subset the change looks like it needs
php artisan config:clear && php artisan config:cache
php artisan route:clear  && php artisan route:cache
php artisan view:clear   && php artisan view:cache

sudo systemctl restart bigkas-queue   # drop any job referencing removed code
sudo systemctl restart php8.3-fpm

php artisan up
Do not skip a cache rebuild

On 8 October 2026 a pull was deployed with only config:cache and view:clear. A new route was missing from the stale bootstrap/cache/routes-v7.php, so route() threw inside a Blade view and the admin dashboard 500'd — with a stack trace pointing at View->renderContents(), which reads like a view bug and sends you hunting in the wrong file. A rollback removes routes, which is exactly the same trap in reverse. php artisan optimize does all three; optimize:clear is the inverse.

To read a 500 there, tail is useless (Laravel writes one long line):
grep -oE '(local|production)\.(ERROR|CRITICAL):.{0,500}' storage/logs/laravel.log | tail -2

9.6 Stopping the lane before a rollback

Reusing RescoreQueue makes this markedly simpler than the draft's version, because there is no serialized job payload to go stale. As its docblock puts it: "Nothing is held anywhere else, so nothing can be lost from a queue that was never written." Pending work is just rows that match a scope — roll the code back and the scope reverts with it.

So there is nothing to drain and nothing to clear. The only requirement is that a scoring run is not mid-flight while the code changes underneath it:

# 1. stop the scheduler from starting another run
sudo crontab -e        # comment out the `schedule:run` line
#    (or, if the cron entry is in /etc/cron.d/, move the file aside)

# 2. let any in-flight run finish — it is at most one recording away from done
ps aux | grep '[a]ssessments:rescore'

# 3. roll back (§9.5), then restore the cron line

# 4. if a run was killed rather than allowed to finish, release its lock —
#    otherwise NOTHING is rescored until the 120-minute window expires
php artisan schedule:clear-cache

No learner data is at risk at any point. Audio and comprehension answers are persisted the moment they arrive; a rollback mid-batch leaves every recording on disk, still owed a score, and the single-child Analyze button can score any of them by hand. A batch interrupted by a rollback resumes by itself once the cron line is restored.

If the rollback crosses the Phase 2 migration

migrate:rollback drops batch_id. Entries that were owed a score because they were batch entries become ordinary unscored recordings, which the original awaitingRescore rules will claim only once they are failed or 15-minutes stale in processing. They are not lost — they are merely slower to be picked up, and Analyze still works on each. Worth telling the teacher rather than letting them think the batch vanished.

10. Out of scope

Each of these is a clean follow-up once the queue is proven in a real classroom — none is blocked by this design.

  • Parallel Whisper. CPU-bound, ≈1 GB resident per model, 4 GB host. Concurrency 1 is the correct setting, not a limitation to work around.
  • Fixing the queue:work timeout in the systemd unit (§8) — latent, harmless, and no longer touched by this work.
  • GPU inference. Different hosting conversation entirely.
  • Websockets / live push. Polling matches the existing pollSession and needs no new infrastructure.
  • Batch-level PDF or Form 3 export. Per-child export already works.
  • Cross-batch analytics and trend comparison.
  • Bulk verdict acceptance. Excluded on purpose — see §2.
The expectation to set with teachers

A 15-child batch is roughly 25–45 minutes of transcription after the last child stops reading. This design makes that wait visible, interruptible and safe to walk away from. It does not make it shorter — on this hardware, nothing in software can.
