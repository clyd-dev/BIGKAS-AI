Batch Assessment

Implementation plan & pipeline specification — BIGKAS‑AI

Date 9 October 2026 Status Awaiting go signal — not implemented Branch master @ 72b0f9d Approach A (delegate)

1. What this builds

A teacher sets up one batch covering up to 15 children. Each child's recording is captured either on their own device or by the teacher one at a time. Every recording is queued for analysis, and the teacher tracks the whole group from a single board that reports honest progress and a real time estimate.

Decisions locked

  • Recording modeBatch holds a roster; each child is self (own device) or teacher (teacher-led), set per child.
  • MaterialOne batch default, overridable per child. Grade policy runs per child, unchanged.
  • Assessment typeAll three supported — oral_reading, comprehension, combined — one type per batch.
  • AnalysisEverything queued. Live progress board with polling. Teacher may close the laptop and return.
  • GuardrailHard roster cap of 15, plus a wait estimate computed from measured job durations.
  • Single-child flowBehaviour frozen. Batch is a separate route and view; the only change to the existing screen is one added link.
  • VerdictStays per child. No bulk-accept button.

2. Capacity: why the design looks like this

The shape of this feature is dictated by one measurement: local Whisper is CPU-bound and strictly serial. The Random Forest, by contrast, is free.

StageCostRuns in parallel?

ml-service/app.py:87		 ≈1–3 min per 1-minute reading on the VPS CPU; ≈1 GB resident No. Running ten at once thrashes the CPU and slows all ten. This is the bottleneck.

Alignment & miscue analysis (PHP) fast Fine

Two consequences follow, and they are not negotiable by UI design:

  1. Analysis must leave the HTTP request and run as a queued job on exactly one worker. Ten synchronous analyses would also pin ten PHP‑FPM workers for minutes and gateway-timeout anyway.
  2. "Assess ten at once" is true for recording and false for analysis. Results trickle in over 25–45 minutes. The board must say so rather than spin.
Model quality — why there is no bulk-accept

The shipped RF reports cv_accuracy 0.4993 (±0.105) and test_accuracy 0.625, and class 4 (Reading Comprehension) was trained on 3 samples. Batch assessment multiplies how many of these predictions a teacher sees at once. The board therefore presents RF output as a suggestion awaiting the teacher, keeps the existing per-child verdict step (AssessmentVerdictController) mandatory, and offers no "accept all" control. Ten unreviewed predictions accepted in one click is the single thing this feature must not make easy.

3. The tension, and the resolution

Single-child behaviour must not change. But AssessmentController::analyze() (app/Http/Controllers/AssessmentController.php:242–372) is ~130 lines of pipeline living inside a controller method that returns HTTP responses, and a queued job cannot call a controller action. There were only two routes forward:

OptionEffect on single-childCost
Delegate
SELECTED		 Route, request shape, JSON responses, status codes and side effects stay identical. The method body becomes ~30 lines calling a new service. Behaviour untouched; the file is edited. One careful refactor, guarded by tests written before it.
Zero-touch AssessmentController.php never opened. The job carries its own copy of the 130 lines. Two divergent copies of the RF, weakness-evidence and provenance logic. A fix in one silently misses the other — and WeaknessEvidence::statuses() is exactly the rule that must never fork. Rejected.
How "untouched" is proven, not claimed

Before anything is refactored, characterization tests pin the current behaviour of analyze(). Most of that net already exists — ReanalyzeAssessmentTest, SpeechEngineRequiredTest, RecordingKeptTest, WeaknessMatchesEvidenceTest, MiscueDetectionTest, ComprehensionTestTest, DecisionSupportTest. All must pass after the refactor with no edits to the test files. If a test needs changing to go green, behaviour changed, and the refactor is wrong.

4. The new pipeline, in detail

4.1 Today — synchronous, inside the request

POST /assessments/{id}/analyze
  └─ AssessmentController::analyze()        ← validation + 130 lines of pipeline + 3 HTTP branches
       teacher's browser waits 1–3 minutes, holding one PHP-FPM worker

4.2 After — one pipeline, two callers

  SINGLE-CHILD (unchanged for the teacher)        BATCH (new)
  POST /assessments/{id}/analyze                  POST .../upload-audio  →  queue
       │                                                │
       ▼                                                ▼
  AssessmentController::analyze()                  AnalyzeAssessmentJob
   • validate, keepRecording()                      • queue: analysis, concurrency 1
   • 3 HTTP response branches                       • tries 2, timeout 420s
   • returns JSON, as it does today                 • ShouldBeUnique on assessment id
       │                                                │
       └──────────────────┬─────────────────────────────┘
                          ▼
            App\Services\AssessmentAnalysisPipeline
              run(Assessment $a, ?array $answers = null): AssessmentResult
              • knows nothing about HTTP
              • throws on failure; callers decide what that means

The pipeline is the single source of truth for how a reading is scored. Both callers get identical results because there is only one implementation.

4.3 Inside AssessmentAnalysisPipeline::run()

Moved verbatim from analyze() — same order, same rules. The ordering is not incidental: comprehension answers are recorded first so that a Whisper failure can never cost the learner's answers.

1Record comprehension answers
Via ComprehensionService::record() when the assessment needs a test. Answers already submitted from the learner's own portal are kept as-is. Runs before any transcription — a failure further down never discards them. Missing answers abort the run here, before a minute of CPU is spent.
▼
2Stamp analysis_started_at
New, additive. Starts the duration clock. Invisible to the single-child flow; feeds the batch estimator.
▼
3Speech to text
SpeechToTextService::transcribe() against the saved audio copy, so what the teacher plays back is what was analysed. Priority order unchanged: local Whisper → OpenAI cloud (if keyed) → placeholder (local/testing only). This is the 1–3 minutes. Throws SpeechServiceUnavailable when no engine answers.
▼
4Alignment & reading metrics
ReadingAnalyzerService::analyze() — transcript vs. reference text. Produces accuracy, WPM, fluency, the miscue breakdown and the 12-feature ML vector. Pure PHP, fast.
▼
5RF classification
MLClassificationService::classify() posts the 12 features to Flask /api/classify. Milliseconds. Falls back to the rule-based classifier when the model is absent — recorded in provenance either way.
▼
6Reconcile prediction against measured evidence
resolveWeaknessId() + WeaknessEvidence::statuses(). A weakness is only stored when the measured numbers support it, so a result never names a skill the teacher's own rows call fine. The rule that must never be duplicated — the whole reason for delegate over zero-touch.
▼
7Merge comprehension score
The real score from the question set replaces the estimate when a test was taken. The ML feature vector is deliberately left untouched.
▼
8Build provenance
Which STT engine ran, whether it was mock, mean word confidence, whether the classifier was ML or rule-based, model version (read from the shipped model_metadata.json, not a second service call), timestamp. This is what AnalysisAdvisorService uses to tell the teacher how far to trust the result.
▼
9Persist result + stamp analysis_duration_ms
$assessment->createResult(), status → completed, ActivityLog entry. The duration stamp is new and additive, written on every run including single-child — so the batch estimator is fed by real measurements from day one instead of a guessed constant.
▼
✕On failure — the pipeline throws; the caller decides
Single-child: unchanged — markFailed(), then 503 with $e->forTeacher() for a dead engine, or 500 with the actionable generic message. Detail goes to the log only.
Batch: SpeechServiceUnavailable → fail immediately, no retry; retrying into a dead engine would burn 10 × 5 min for nothing. The batch is marked engine_unavailable and the board says so once: "speech engine offline — your recordings are saved, retry when it's back." Any other exception → one retry, then markFailed(). A failed child never stops the batch. The recording always survives; re-analysing is all it takes.

4.4 Batch state machine, per child

waiting ──recording captured──▶ recorded ──enqueued──▶ queued
                                                          │
                                              worker picks it up
                                                          ▼
                                                    transcribing
                                        ┌─────────────────┴─────────────────┐
                                     success                            failure
                                        ▼                                  ▼
                                 needs verdict                          failed
                                        │                         (retry → queued)
                            teacher decides (per child)
                                        ▼
                                      done

Batch status: collecting ─▶ analyzing ─▶ completed
                   └──────────────────────▶ cancelled
                   └──────────────────────▶ engine_unavailable (recoverable)

The batch reaches completed when every entry is terminal (done or failed). A failed entry does not block completion — it is reported, retryable, and the batch moves on.

4.5 Wait estimate

New App\Services\AnalysisQueueEstimator. Takes the median of the last 20 analysis_duration_ms values (seeded at 150 s until data exists), multiplies by queue depth ahead of the given child, and returns a per-child ETA, a batch ETA, and how many jobs ahead belong to other teachers. Median, not mean, so one 5-minute outlier does not distort every estimate on screen.

The board shows this as "about 18 min remaining · 4 ahead of you from other classes". Teachers self-regulate when they can see the truth, and a slow queue becomes distinguishable from a broken one.

Added to assessments — all nullable, all additive

ColumnNotes
batch_idNullable FK, indexed. NULL means single-child. Every existing row stays NULL; every existing query keeps working; the single-child flow never writes it.
recording_modeself / teacher. Batch-only.
queued_at, analysis_started_at, analysis_duration_msQueue and timing telemetry; feeds the estimator.

Deliberately not added

  • No roster-entry table. A roster entry is an Assessment. Per-child material override is simply that child's existing material_id.
  • No join-code table. Self-record reuses one AssessmentSession per entry, with the existing generateCode() and student join flow.
New status constant — the one place to be careful

Assessment::STATUS_QUEUED joins the existing five. The single-child flow never sets it, so no existing check changes meaning — but that must be verified, not assumed. Before this ships, every status comparison and every whereIn([...]) in the codebase gets grepped and read, to confirm the new value cannot fall through a condition written when there were only five states. Assessment::canRetry() and needsAnalysis() are the first two to check.

6. Teacher-facing UI

Built on the existing staff shell and <x-page-header>. The board is a nav page, so no back link; each child drills down to the existing results screen with a back link labelled "Batch", per the house rule that PageHeaderTest enforces.

Entry point

/assessments/new gains one added link — "Assess a group" — pointing at the new assessments/batch/create. The existing single-learner screen is otherwise not modified.

Batch setup — /assessments/batch/create

Pick a class or hand-pick learners → language → type → default material → a roster table where each row can override the material and choose self or teacher. The cap comes from config('assessment.batch_max_learners'), default 15, enforced in validation with a clear message. Grade policy runs per child under today's rules: a cross-grade child must be ticked individually, never silently.

Batch board — /assessments/batch/{batch}

The roster, polling /batch/{batch}/poll — the same polling pattern as the existing pollSession, so no new transport. Each row shows a state chip (waiting / recorded / queued / transcribing / needs verdict / done / failed), the ETA, and one action.

  • Teacher-led rows record inline, reusing _audio_capture.blade.php.
  • Self-record rows display the child's join code.
  • Comprehension answers come from the child's own device in self mode, or from an inline per-child panel in teacher-led mode — posted through the existing ComprehensionService path before the job is queued.
  • Failed rows offer per-child Retry, with today's retry semantics.

7. Build order

Each phase is independently green and independently revertible. A phase does not start until the one before it is proven.

Phase 0 — Safety netno production code

Pin the current behaviour of analyze(): the success JSON (redirect_url), the 503 on a dead engine, the 500 on generic failure, the markFailed side effect, the comprehension-before-STT ordering, and the recording surviving a failed analysis. Fill whatever gap the existing seven tests leave. These tests are never edited afterwards.

Phase 1 — Extract the pipelinegate: all Phase 0 tests green,
zero test-file edits

Create AssessmentAnalysisPipeline; move the nine steps and buildProvenance() into it verbatim. analyze() keeps its validation, keepRecording(), status transition and all three response branches, and calls the pipeline in the middle.

Phase 1 ships with zero new features. It is a pure, behaviour-neutral refactor — and the gate before anything else begins.

Phase 2 — Schemagate: migrate:rollback verified clean

assessment_batches + the nullable columns on assessments + STATUS_QUEUED, plus the status-check audit described in §5. Every migration carries a working, tested down().

Phase 3 — Queuegate: 15 jobs run serially on the VPS
without a timeout kill

AnalyzeAssessmentJob (the app's first job), AnalysisQueueEstimator, and the systemd fix in §8. Verified with a real 15-recording run against local Whisper, not just in tests.

Phase 4 — Teacher UIgate: one real classroom batch end to end

Setup screen, batch board, polling, inline recording, per-child comprehension panel, retry.

Phase 5 — Testsgate: full suite green

Batch creation, cap enforcement, per-child grade policy, batch_id null-safety across existing queries, job enqueued on upload rather than on create, serial execution, a failed child leaving the batch alive, engine-offline pausing without burning retries, estimator maths, poll payload, and authorization — teacher A cannot see teacher B's batch; admin stays read-only, per the LearnerAdminReadOnlyTest precedent. Plus the entire Phase 0 suite still green.

8. Latent bug this work exposes

The installed queue worker would kill every Whisper job

bigkas_first_day_setup.sh:285 installs:

ExecStart=/usr/bin/php artisan queue:work --sleep=3 --tries=3 --max-time=3600

Laravel's default per-job timeout is 60 seconds. A 300-second Whisper transcription would be killed mid-run, every time. The unit needs --queue=analysis --timeout=420 --tries=2.

Nobody has hit this because the worker is installed but app/Jobs/ is empty — it has never run a job. Batch assessment is what first puts work on that queue, so the fix belongs to Phase 3, and docs/deployment-vps.md must carry it too.

9. Backup & rollback

Six independent ways back, strongest first. The first two mean that in the common case nothing has to be rolled back at all.

9.1 Feature flag — the instant off switch

BATCH_ASSESSMENT_ENABLED=false behind config('assessment.batch_enabled') hides the "Assess a group" link and makes every batch route 404. The single-child flow is untouched code either way, so it keeps working.

This ships off. It is turned on deliberately, and turning it back off takes one .env edit — no code rollback, no migration rollback, no downtime. Remember that an .env edit does nothing until config:cache runs again.

9.2 Branch + tag

Before any work starts:

# on the dev machine, from clean master
git tag -a pre-batch-assessment -m "Last state before batch assessment work"
git push origin pre-batch-assessment
git switch -c feat/batch-assessment

master is never committed to during the build. The tag is a permanent, named return point — the repo has no tags today, so this is also the project's first.

9.3 One commit per phase

Each phase lands as its own commit, each independently green. Rollback granularity is therefore a phase, not the whole feature. Phase 1 in particular — the pipeline extraction — is behaviour-neutral and committed alone, so if anything about it smells, that single commit reverts without touching the schema or the queue.

9.4 Database

Every schema change is additive: one new table, and nullable columns on assessments. Nothing is renamed, retyped or dropped, so no existing data can be lost and down() is genuinely safe. Each migration's down() is written and exercised (migrate:rollback) before the phase is called done.

On the VPS, before migrating:

# dump first — takes seconds, and is the thing you will wish you had
mysqldump -u <user> -p <database> > ~/backups/bigkas-$(date +%F-%H%M).sql

php artisan migrate
# if it goes wrong:
php artisan migrate:rollback --step=1

Recorded audio under storage/app/public/assessments/audio is only ever added to by this work, never deleted or rewritten, so it needs no special handling. A routine copy alongside the dump costs nothing if you want belt and braces.

9.5 Full VPS rollback procedure

If the feature flag is not enough and the deployment itself has to go back:

cd /var/www/bigkas-ai

php artisan down                      # maintenance mode

git checkout pre-batch-assessment     # or: git checkout master
php artisan migrate:rollback --step=<n>   # only if migrations had run

# all THREE caches, always — not the subset the change looks like it needs
php artisan config:clear && php artisan config:cache
php artisan route:clear  && php artisan route:cache
php artisan view:clear   && php artisan view:cache

sudo systemctl restart bigkas-queue   # drop any job referencing removed code
sudo systemctl restart php8.3-fpm

php artisan up
Do not skip a cache rebuild

On 8 October 2026 a pull was deployed with only config:cache and view:clear. A new route was missing from the stale bootstrap/cache/routes-v7.php, so route() threw inside a Blade view and the admin dashboard 500'd — with a stack trace pointing at View->renderContents(), which reads like a view bug and sends you hunting in the wrong file. A rollback removes routes, which is exactly the same trap in reverse. php artisan optimize does all three; optimize:clear is the inverse.

To read a 500 there, tail is useless (Laravel writes one long line):
grep -oE '(local|production)\.(ERROR|CRITICAL):.{0,500}' storage/logs/laravel.log | tail -2

9.6 Draining the queue before a rollback

Jobs are serialized with a class name. Rolling back code while analyze jobs sit in the jobs table leaves rows referencing a class that no longer exists, and the worker will fail them in a loop.

# before checking out the older code:
php artisan queue:pause        # stop taking new work (or: systemctl stop bigkas-queue)

php artisan queue:clear analysis   # discard pending jobs — recordings are SAFE,
                                   # they stay on disk and can be re-analysed later

This loses no learner data. The audio and the comprehension answers are already persisted; only the pending instruction to analyse is discarded, and the single-child Analyze button can re-run any of them.

10. Out of scope

Each of these is a clean follow-up once the queue is proven in a real classroom — none is blocked by this design.

  • Parallel Whisper. CPU-bound, ≈1 GB resident per model, 4 GB host. Concurrency 1 is the correct setting, not a limitation to work around.
  • GPU inference. Different hosting conversation entirely.
  • Websockets / live push. Polling matches the existing pollSession and needs no new infrastructure.
  • Batch-level PDF or Form 3 export. Per-child export already works.
  • Cross-batch analytics and trend comparison.
  • Bulk verdict acceptance. Excluded on purpose — see §2.
The expectation to set with teachers

A 15-child batch is roughly 25–45 minutes of transcription after the last child stops reading. This design makes that wait visible, interruptible and safe to walk away from. It does not make it shorter — on this hardware, nothing in software can.
