BIGKAS-AI: Chapters 1 to 3 vs the Built System

Does the system we built match what the paper says it is, and what it set out to do?

Document reviewed: docs/IT-B8-Soquita-BIGKAS-AI_revised2.docx (Chapters I to III, references) · System reviewed: this repository at master (HEAD 2b45292) · Review date: 2026-10-12
Method: read the full text of the three chapters, then checked each claim against routes, services, models, migrations, ml-service/ (app, training scripts, model_metadata.json, labelled dataset), the README and the test suite. Nothing was run against the live server, so runtime behaviour is judged from code and stored artefacts only.

For the panel: two plain-language explainers sit at the end of this file. Part A, how a mispronunciation, substitution, omission, repetition or insertion is detected and Part B, how a reading is judged phonemic, decoding, fluency or comprehension.

1. Bottom line

The system delivers what the objectives ask for.

Objectives 1 and 2 (the assessment and intervention engine, and role-based dashboards) are implemented end to end, and in several places go further than the paper describes. Nothing in the objectives is missing from the product.

The paper describes a different system in a handful of places, and a panel can find them.

The gaps are not missing features. They are statements in Chapters 1 to 3 that the repository contradicts or cannot back up: which speech engine runs, what the training data covers, whether audio is encrypted, which evaluation metrics were actually produced, and which questionnaire is used. Most are fixed by editing the paper. Two (audio storage, WER measurement) are small system or evidence tasks.

Part A. How the system knows what kind of reading mistake it is

Written for panelists who are not programmers. Every rule below is quoted from the source file and line shown, and the worked example at the end is the real output of the system's own code (run on 2026-10-12), not a mock-up.

A1. The idea in one minute

The system does not "hear" pronunciation the way a teacher's ear does. It compares written words.

A speech-to-text engine writes down what the child said. The system lines that text up against the passage and applies a short list of rules to every place the two differ. Each rule is something a teacher would also check: was the word skipped, replaced by something that sounds alike, replaced by something unrelated, said twice, or added?

1. Child readsTeacher or student records the passage.
2. Speech to textWhisper writes each word with its start time, end time and confidence.
3. Line upSpoken words are placed opposite the passage words.
4. Name each differenceRules label it: omission, mispronunciation, repetition...
5. Count and scoreAccuracy, words per minute, reading level.

A2. Step 3: lining up the child's words with the passage

In plain words. Picture two strips of paper, one with the passage and one with what the child said. Slide them so that as many words as possible sit opposite their partner, using as few changes as possible. Whatever cannot be matched falls into one of three piles: a passage word with nothing opposite it (skipped), a spoken word with nothing opposite it (extra), or two different words facing each other (replaced).

This is the "Levenshtein / edit distance" method named in Chapter 3. The program tries every line-up and keeps the cheapest one.

Formula cost of a matched word pair = −1 (a reward)
cost of any edit (skip, extra word, replacement) = m + n + 1  where m = passage words, n = spoken words
choose the line-up with the lowest total cost; on a tie, keep the earliest matches so unread words fall at the end
$edit = $m + $n + 1;                                          // cost of any edit
$step = $reference[$i - 1] === $spoken[$j - 1] ? -1 : $edit;  // a match earns 1 back
$dp[$i][$j] = min(
    $dp[$i - 1][$j] + $edit,        // passage word skipped   (omission)
    $dp[$i][$j - 1] + $edit,        // extra spoken word      (insertion)
    $dp[$i - 1][$j - 1] + $step     // matched or replaced word
);

Source: app/Services/ReadingAnalyzerService.php lines 527–548 (alignTexts). Before this step, both texts are lower-cased and stripped of punctuation (tokenizeText, lines 326–332), so capital letters and commas never count as mistakes.

Why the edit cost is large. The code comment (lines 517–526) explains that a match is only allowed to break a tie, never to justify an extra edit. So the line-up always has the fewest edits first, and only then the most matches.

A3. Step 4: naming each difference

The line-up only knows three things: matched, replaced, or no partner. MiscueClassifierService turns those into the labels a reading teacher uses. The rules are applied in this order (lines 63–67), so a word can only receive one label:

$this->markOffPassageAndPhraseRepetitions($details); // 2. long runs of extra words
$this->markSingleInsertions($details);              // 3. single extra words
$this->markReplacements($details);                  // 4. replaced words
$this->markPauses($details);                        // 5. silences between words

Formula: "sounds like" (how a replaced word becomes a mispronunciation) similarity(a, b) = 1 − Levenshtein(a, b) ÷ length of the longer word
sounds like = similarity ≥ 0.5, OR Soundex(a) = Soundex(b), OR Metaphone(a) = Metaphone(b) (the last two only for plain a–z words)
private function soundsLike(string $a, string $b): bool
{
    if ($this->similarity($a, $b) >= 0.5) { return true; }
    if (preg_match('/^[a-z]+$/', $a) && preg_match('/^[a-z]+$/', $b)) {
        return soundex($a) === soundex($b) || metaphone($a) === metaphone($b);
    }
    return false;
}

A6. What a panelist should know about the limits

  • It reads text, not sound. If the speech engine quietly writes the correct word for a mispronounced one, the mistake is invisible. The file header says so (lines 27–30). The Flask service reduces this by prompting Whisper to keep stumbles and not to reuse its own earlier output (ml-service/app.py, VERBATIM_PROMPTS and condition_on_previous_text = False).
  • "Mispronunciation" means "a wrong word that looks or sounds like the right one." The system cannot tell a slip of the tongue from a wrong guess.
  • The numbers 0.5, 1 s, 3 s, 2 words and 60% are design choices, not DepEd rules. Only the Phil-IRI cut-offs (97 / 90 for word reading, 80 / 59 for comprehension) come from DepEd.
  • Not yet compared with a teacher's own marking of the same recordings (README: "no end-to-end validation"). A simple check before the defense: have a teacher mark 15 to 20 recordings by hand and compare the counts per category.

Part B. How the system decides: phonemic, decoding, fluency or comprehension

B1. The idea in one minute

Two things happen, and they must agree.

First, four simple checks look at the evidence for each skill and give it a colour: green (OK), amber (watch) or red (concern). These are rules a teacher can follow with a pencil.
Second, a machine-learning model (Random Forest) suggests one main weakness. The system only keeps the suggestion if the matching check is amber or red. This is called the evidence gate.

The teacher always sees all four colours, and can accept, override or invalidate the stored weakness.

B3. Where machine learning comes in, and why the gate exists

What the model sees. Twelve numbers computed from the reading: accuracy, words per minute, a 0–10 fluency score, and rates for substitutions, omissions, insertions, three sound-pattern shares, self-corrections, pauses and a 0–10 expression estimate (ReadingAnalyzerService.php lines 103–116).

What it does. A Random Forest is a committee of 100 small decision trees. Each tree votes for one of five labels (0 none, 1 phonemic, 2 decoding, 3 fluency, 4 comprehension); the share of votes becomes the probability shown. It was trained on 519 teacher-confirmed clips (see section 3.2, L3).

Why a gate. The three sound-pattern numbers are shares of the reader's mistakes, not counts per word. A single vowel-like slip makes the share 100%, so the model (and the older hand-written rules) kept answering "phonemic awareness" for readers whose real trouble was decoding or pace. The source comment says exactly this (WeaknessEvidence.php lines 8–24).

The evidence gate, step by step 1. Take the model's highest-probability label.
2. Keep it if it is "no weakness" (0), or if that skill's check is amber or red.
3. Otherwise go down the model's ranking and keep the first label that is "no weakness" or has an amber/red check.
4. If none qualifies, store the clearest measured problem (red before amber, lower skill number on ties). If nothing shows a problem, store no weakness.

What the gate does with it

B5. Things to be ready to explain

  • The model leaned towards "Comprehension" here although it saw only 3 comprehension examples in training. That is the reason the gate exists: a comprehension label is never stored unless the quiz backs it. Say this plainly if asked; do not describe the forest as measuring comprehension.
  • Two different "skill" displays exist in the code. The four coloured rows on the results page use the rules in B2. The skill-breakdown bars on the learner profile, parent report and learner report come from an older estimate (Learner::getSkillBreakdown(), Learner.php lines 226–250, reading ReadingAnalyzerService::calculateSkillScores() lines 901–924). In that estimate "phonemic" is 100 minus 10 per sound-pattern slip and "comprehension" is accuracy × 0.3 + fluency × 7, a guess even when the real quiz score exists. The two can disagree. Recommended fix: feed the bars from the B2 results (quiz score for comprehension).
  • Accuracy of the suggestion is modest (62.5% test, about 50% cross-validated, 41% majority baseline). That is why the stored weakness is presented as a suggestion with the measured evidence beside it, and why the teacher has the final say.
  • Recommendations come after the weakness. The activities shown on the results page are a look-up by stored weakness and grade (Assessment::getRecommendedInterventions()), so any error in the weakness carries through to the activities.
