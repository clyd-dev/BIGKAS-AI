A. Prepare on your laptop Laptop

The server only gets what is on GitHub. Anything uncommitted stays on your machine.

A1 Run the tests

Catch a broken build before the server does.

cd F:\MyApp\BIGKAS-AI
php artisan test
ExpectedTests: NN passed Duration: ...

Any failure means stop and fix it first.

A2 Check what you are about to commit

A 1.6 GB training zip once blocked a push. Look for anything large, secret, or unintended.

git status --short
git diff --stat | tail -1
Never commit
  • .env (secrets), ml-service/venv/, audio files, *.zip
  • Anything over about 50 MB. GitHub refuses files over 100 MB.

Stage files by name or by folder when unsure. Use git add -A only after reading the status above.

A3 Commit and push

git add -A
git commit -m "feat: describe what changed"
git push origin master
ExpectedTo https://github.com/clyd-dev/BIGKAS-AI.git abc1234..def5678 master -> master

Confirm it landed: git status -sb should show ## master...origin/master with no "ahead".

A4 Note what changed

This decides which optional steps you need on the server (B5 front-end build, B6 migrations).

git diff --stat HEAD~1 -- package.json resources/js resources/css database/migrations ml-service
If the diff touchesYou need on the server
resources/js, resources/css, package.jsonB5 (npm run build)
database/migrationsB6 (migrate), already in the standard flow
ml-service/B8 restart bigkas-ml; also pip install if requirements.txt changed

B. Deploy on the server Server

B0 Connect

ssh root@84.247.158.7

The prompt should look like root@vmi...:~#. Then move into the app folder for everything below:

cd /var/www/bigkas-ai

B1 Take a backup first

If the deploy goes wrong, this is your way back (see section D).

/usr/local/bin/bigkas-backup.sh && ls -lh /backups | tail -n 4
Expected-rw------- 1 root root 1.2M Oct 20 14:02 db_20261020.sql.gz -rw------- 1 root root 85M Oct 20 14:02 storage_20261020.tar.gz

Both files should have today's date and a non-zero size.

B2 Make sure the server copy is clean

Never edit code on the server. Local changes there make git pull fail.

git status --short
Expected(no output)

If files are listed, see "git pull refuses" in section E.

B3 Pull the new code

git pull origin master
ExpectedFrom https://github.com/clyd-dev/BIGKAS-AI abc1234..def5678 master -> origin/master Updating abc1234..def5678 Fast-forward NN files changed, NNN insertions(+), NN deletions(-)

"Already up to date" means your push did not reach GitHub. Go back to A3.

B4 Install PHP dependencies

COMPOSER_ALLOW_SUPERUSER=1 composer install --no-dev --optimize-autoloader --no-interaction
ExpectedInstalling dependencies from lock file Generating optimized autoload files No security vulnerability advisories found.

B5 Build the front end (only if JS, CSS or package.json changed)

npm ci --no-audit --no-fund && npm run build
Expectedvite v... building for production... ✓ built in 8.52s

Skipping this when only PHP or Blade files changed is fine.

B6 Migrate the database

Run this before any analysis happens. New columns (for example classification_status) must exist first.

sudo -u www-data php artisan migrate --force
ExpectedINFO Running migrations. 2026_10_xx_xxxxxx_add_classification_status ........ DONE or: INFO Nothing to migrate.

Want to preview first? Run php artisan migrate --pretend.

B7 Rebuild all three caches

Do all three, every time

A previous deploy rebuilt only config and view. The stale route cache lacked the new route, so the admin dashboard threw a 500 from inside a Blade view. The error looked like a view bug but was not.

sudo -u www-data php artisan config:clear && sudo -u www-data php artisan config:cache
sudo -u www-data php artisan route:clear  && sudo -u www-data php artisan route:cache
sudo -u www-data php artisan view:clear   && sudo -u www-data php artisan view:cache
ExpectedINFO Configuration cache cleared successfully. INFO Configuration cached successfully. INFO Route cache cleared successfully. INFO Routes cached successfully. INFO Compiled views cleared successfully. INFO Blade templates cached successfully.

Run them as www-data. If you run them as root, the cache files become root-owned and PHP cannot rewrite them.

B8 Fix permissions and restart services

chown -R www-data:www-data storage bootstrap/cache
chmod -R 775 storage bootstrap/cache
systemctl reload php8.3-fpm
systemctl restart bigkas-ml bigkas-queue

The queue worker keeps old code in memory until restarted. The Flask service restart loads the new model files and the new /api/health fields. Whisper takes about 20 to 60 seconds to load again.

If requirements.txt changed, install first:

sudo -u www-data ml-service/venv/bin/pip install -r ml-service/requirements.txt
systemctl restart bigkas-ml

B9 One-time post-upgrade command (first deploy of the "never score without a measurement" change only)

Recomputes learner levels after readings that were not measured from the child's voice are excluded. Preview, then apply.

sudo -u www-data php artisan learners:recompute-levels --dry-run
sudo -u www-data php artisan learners:recompute-levels

Skip if you already ran it on this server.

C. Verify Server + browser

C1 All services are running

systemctl is-active nginx php8.3-fpm mysql bigkas-ml bigkas-queue
Expectedactive active active active active

C2 The ML service is up with the model loaded

curl -s http://127.0.0.1:5000/api/health; echo
journalctl -u bigkas-ml -n 20 --no-pager

The health JSON must report the classifier as loaded. If it does not, the app saves results as "classification unavailable" instead of guessing a weakness. That is the intended behavior, so a missing model is a real outage, not a cosmetic one.

C3 No new errors in the Laravel log

Laravel writes each error on one very long line, so tail is hard to read. This pulls out just the error heads.

grep -oE '(local|production)\.(ERROR|CRITICAL):.{0,300}' storage/logs/laravel.log | tail -n 3
Expected(nothing from today)

C4 The scheduler is firing

The app runs health:check every minute and assessments:rescore every five minutes, so outage alerts depend on it.

sudo -u www-data php artisan schedule:list
cat /etc/cron.d/bigkas-scheduler

One-shot script (when you know the steps)

Once you have done the steps by hand a couple of times, this does B1 to B8 in order and stops at the first error. Save it as /root/redeploy.sh and run bash /root/redeploy.sh.

#!/usr/bin/env bash
set -euo pipefail
cd /var/www/bigkas-ai
art() { sudo -u www-data php artisan "$@"; }

echo "==> backup";     /usr/local/bin/bigkas-backup.sh
echo "==> pull";       git pull origin master
echo "==> composer";   COMPOSER_ALLOW_SUPERUSER=1 composer install --no-dev -o --no-interaction
echo "==> frontend";   npm ci --no-audit --no-fund && npm run build
echo "==> migrate";    art migrate --force
echo "==> caches";     art config:clear && art config:cache
                     art route:clear  && art route:cache
                     art view:clear   && art view:cache
echo "==> permissions"; chown -R www-data:www-data storage bootstrap/cache
                     chmod -R 775 storage bootstrap/cache
echo "==> restart";    systemctl reload php8.3-fpm
                     systemctl restart bigkas-ml bigkas-queue
echo "==> status";     systemctl is-active nginx php8.3-fpm mysql bigkas-ml bigkas-queue
echo "Deployed: $(git log --oneline -1)"
Still verify by hand

The script cannot tell you the app works. Always finish with section C, at least the browser click-through.
